从零打造低延迟 Windows HomeLab：公网 IPv6 + DDNS-GO + NPM 反向代理

发表于 2026-08-09 更新于 2026-08-10 分类于 HomeLab ， 网络配置 阅读次数：

在以往的 HomeLab 搭建中，本地服务的公网暴露往往依赖 Cloudflare Tunnel 或各类内网穿透工具。然而，由于中转服务器大多位于海外，这种方案普遍存在高延迟、带宽受限以及连接不稳定等痛点。
随着国内运营商家庭宽带普遍普及原生 IPv6，光猫改桥接后由路由器进行 PPPoE 拨号，设备即可获取到直连公网的 IPv6 地址。本文将详细介绍如何在 Windows 11 环境下，利用公网 IPv6、DDNS-GO 以及 Docker 版 Nginx Proxy Manager (NPM)，实现低延迟、安全且带 HTTPS 证书的本地服务外网暴露。

前提条件：本文方案建立在拥有原生公网 IPv6 的基础之上。在开始前，请先前往 test-ipv6.com 检测你的网络环境是否符合要求。

背景与痛点

  • 原始方案：使用 Cloudflare Tunnel，导致高延迟、连接不稳定。
  • 具备一个个人域名：拥有一个个人域名（本文以 haozi.space 为例）。
  • 网络条件：宽带提供原生公网 IPv6，光猫已桥接，路由器负责 PPPoE 拨号。
  • 目标：利用真实 IPv6 直接把 Windows 上的 Jellyfin、Sunshine（Moonlight）等服务暴露到外网，保持最小的网络转发层数，从而获得几乎零延迟的体验。
    需要注意的是，本文的一切前提都在于拥有一个公网IPv6，如果你不知道你自己有没有，可以前往 https://test-IPv6.com 检测一下你的网络环境。

架构总览

适配睿易 (Ruiyi) EW1300 路由器环境的整体架构如下：

  • DDNS‑GO（Windows 原生）：每 5 分钟将本机的公网 IPv6 写入 Cloudflare 的 *.haozi.space AAAA 记录。
  • Nginx Proxy Manager (NPM)：运行在 Docker 中，负责 HTTPS 终止、域名匹配、Let’s Encrypt 泛域名证书。
  • Ruiyi EW1300：直接放行需要的 IPv6 端口，并把外部流量转发到 Windows 主机的局域网 IP。
  • Windows 防火墙：同样放行对应端口，避免本机对 Docker 虚拟网卡的流量拦截。

适用场景与拓展

方案适用场景

  • 4K 原画家庭影音：无需经过中转服务器，直接以全速宽带上行播放 Jellyfin / Emby / Plex 中的高清视频。
  • 超低延迟云游戏：结合 Sunshine + Moonlight 实现随地远程串流 Windows 3A 大作。
  • 私有云存储与同步：搭配 Nextcloud、Obsidian (CouchDB / Remotely Save) 等服务实现全端快速同步。
  • 远程运维与桌面：借助已有的公网 IPv6 + DDNS 解析，可直接通过 RDP（Windows 远程桌面协议）实现低延迟的远程桌面控制，无需中继服务器。对于同时管理多台设备的场景，也可部署 RustDesk 自建Server（需要一台具有公网 IP 的 VPS），统一管理家庭网络内所有无公网 IP 的设备。

后续拓展方向

  • 安全防护强化：在 NPM 中为敏感服务（如管理后台）开启 Access List（ HTTP 基本认证 / IP 白名单），防止公网暴力破解。
  • 动态 IP 变动熔断与通知：利用 DDNS-GO 内置的 Webhook 功能，在 IPv6 地址变更时推送到 Server 酱、Telegram 机器人或 Server 酱。
  • 全局 Fallback 备用方案：由于部分公司网或公共场所 Wi-Fi 可能未开启 IPv6，建议搭配 Tailscale / Netbird 自建 DERP 中继作为纯 IPv4 环境下的备用通道。

为什么Windows上会有很多IPv6地址？ - 知乎

^([0-9a-fA-F]{1,4}:){7}[0-9a-fA-F]{1,4}$
这个正则表达式的意思是：“严格匹配一个由 8 段、用冒号隔开的、每段包含 1 到 4 位十六进制数字的完整 IPv6 地址”。

  1. 边界锚定：^ 和 $
  • ^：匹配字符串的开始位置。
  • $：匹配字符串的结束位置。
  • 作用：确保整个字符串只能包含符合条件的 IPv6 地址，前后不能有任何其他多余的字符。
  1. 核心段落：[a-fA-F0-9]{1,4}
  • [...]：字符集，表示允许出现的字符。
  • a-fA-F0-9：表示允许出现小写字母 a-f、大写字母 A-F、以及数字 0-9（即合法的十六进制字符）。
  • {1,4}：量词，表示前面的字符集必须出现 1 到 4 次。
  • 作用：匹配 IPv6 地址中的单个数群（例如：2001、0db8、85a3 甚至简写的 1）。
  1. 前 7 段的循环：([a-fA-F0-9]{1,4}:){7}
  • (...)：分组，把里面包含的内容看作一个整体。
  • :：普通的冒号，表示段与段之间的分隔符。
  • {7}：量词，表示括号内的整体（即“1-4位十六进制数+冒号”）必须恰好重复出现 7 次。
  • 作用：匹配前 7 段地址。形如：2001:0db8:85a3:0000:0000:8a2e:0370:
  1. 最后一段：[a-fA-F0-9]{1,4}
  • 作用：匹配最后一段不带冒号的十六进制数（第 8 段）。形如：7334

匹配成功示例

  • 2001:0db8:85a3:0000:0000:8a2e:0370:7334 （完美匹配）
  • 2001:db8:85a3:0:0:8a2e:370:7334 （成功，因为每段 1 到 4 位都算合规）

匹配失败示例

  • 2001:db8::1 （失败，因为使用了 :: 缩写，总段数不足 8 段，无法通过 {7} 的硬性计数）
  • 2001:0db8:85a3:0000:0000:8a2e:0370:7334/64 （失败，因为末尾带有 $, 无法匹配 /64 子网掩码）

[^2]:关于填写 Moonlight客户端的注意事项

  1. 为什么 Web 界面和串流是两码事？
  • Sunshine 的 Web UI (配置页面)：这是一个纯网页服务（HTTP）。所以你可以把它挂在 NPM（Nginx Proxy Manager）后面，通过 https://sunshine.haozi.space:8443 访问。它的作用仅仅是让你在外面能打开页面，进行“配对(PIN)”或者修改分辨率等设置。
  • Moonlight 实际串流 (打游戏)：游戏画面传输使用的是一套非常底层的私有协议，主要依赖 UDP 端口 (如 47998) 来保证超低延迟。NPM 默认只代理 HTTP/TCP 流量，NPM 根本无法也不应该去代理游戏串流的 UDP 流量（如果强行用 Nginx 代理 UDP，延迟会激增，失去串流的意义）。

  1. 那么 Moonlight 客户端到底怎么填？
    因为 Moonlight 必须直连你的 Windows 电脑，所以它的逻辑是：
    输入一个地址 → Moonlight 通过 DNS 查到你电脑的真实 IPv6 → 直接向这个 IPv6 的 47998 等端口发起连接。
    所以：
    错误填法：http://vpn.haozi.space 或者 https://sunshine.haozi.space:8443
    （Moonlight 客户端的“添加主机”框里不能带 http:// 或端口号，它不是浏览器，它不认识网址格式）。
    正确填法：vpn.haozi.space 或者 sunshine.haozi.space
    （只需填纯域名。只要这个域名在 DDNS 里绑定了你 Windows 的公网 IPv6 即可）。

  2. 你的疑问解答

“这对吗？我之前认为只要输入 http://vpn.haozi.space 获取了主机的 IPv6 地址就可以串流了”

你的核心思路是对的：确实是靠域名获取主机的 IPv6 地址来进行串流。
不管是叫 sunshine.haozi.space 还是 vpn.haozi.space，只要这个域名在 Cloudflare 的 DNS 记录里（通过 DDNS-GO）指向了你电脑当前的真实 IPv6 地址，Moonlight 就能顺藤摸瓜找到你的电脑。

  1. 串流成功的绝对前提（敲黑板）
    既然 Moonlight 是直连你的电脑，绕过了 Nginx (NPM)，那么：
    你必须在 路由器防火墙 (ip6tables) 和 Windows Defender 防火墙 中，真实地放行 Sunshine 所需的所有端口。仅仅在 NPM 里配置反代是没用的。
    你需要放行的端口列表：
  • TCP: 47984, 47989, 48010
  • UDP: 47998, 47999, 48000, 48002, 48010
