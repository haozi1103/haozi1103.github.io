无光猫超密限制下，老毛子 K2 配置 IPv6 的踩坑过程：实现公网 IPv6 与 Tailscale P2P 直连后，因入站失败与双前缀异常，最终转为 AP 模式并用 Tailscale 兜底远程访问。

在上篇文章 基于原生 IPv6 与 NPM 实现 Win11 本地服务低延迟公网暴露 中，我们讨论了在主路由器能够进行 PPPoE 拨号的理想环境下部署 HomeLab 的全流程。然而在现实的复杂网络中，很多朋友（包括我自己）常会遇到更为棘手的客观限制——没有光猫的超级管理员密码，光猫保持默认路由模式，而自己折腾的路由器（如刷了老毛子 Padavan 固件的斐讯 K2 ）只能充当二级路由。

本文并不是一次 IPv6 配置失败后的修复，而是在已经实现公网 IPv6 获取和 Tailscale P2P 直连之后，对家庭网络结构进行重新优化的一次排查记录。

在江西移动宽带 + 老毛子 K2 二级路由环境下，我先是成功拿到了原生公网 IPv6 出口，并实现了 Tailscale P2P 直连——然而长期使用下来，稳定性和公网入站能力却始终不尽如人意：ddns-go 一直能拿到 IPv6 地址，却无法与 api.cloudflare.com 正常通信、域名记录迟迟更新不了；Tailscale 打洞时好时坏，失败时流量被迫退回位于海外的高延迟 DERP 中转节点（如 sfo 旧金山，延迟高达 400~500ms）。本文将完整还原这段“成功后继续踩坑、最终重构家庭网络结构”的排查全过程。

背景与诉求：没有光猫超级管理员密码，光猫保持默认路由模式。在不修改光猫模式的前提下，让挂载在老毛子 K2 下的 Windows 11 主机获得可用的公网 IPv6，并保证远程访问的长期稳定。

基于原生 IPv6 与 NPM 实现 Win11 本地服务低延迟公网暴露

发表于 2026-08-09 更新于 2026-08-20 分类于 工程
针对传统内网穿透方案高延迟、受限的痛点，本文介绍如何在 Windows 11 环境下利用原生公网 IPv6，结合 ddns-go、路由器转发与 Docker 版 Nginx Proxy Manager (NPM)，实现 Jellyfin、Sunshine 等本地服务的高速低延迟外网直连与 HTTPS 安全访问。

在以往的 HomeLab 搭建中，本地服务的公网暴露往往依赖 Cloudflare Tunnel 或各类内网穿透工具。然而，由于中转服务器大多位于海外，这种方案普遍存在高延迟、带宽受限以及连接不稳定等痛点。
随着国内运营商家庭宽带普遍普及原生 IPv6，光猫改桥接后由路由器进行 PPPoE 拨号，设备即可获取到直连公网的 IPv6 地址。本文将详细介绍如何在 Windows 11 环境下，利用公网 IPv6、ddns-go 以及 Docker 版 Nginx Proxy Manager (NPM)，实现低延迟、安全且带 HTTPS 证书的本地服务外网暴露。

前提条件：本文方案建立在拥有原生公网 IPv6 的基础之上。在开始前，请先前往 test-ipv6.com 检测你的网络环境是否符合要求。

背景与痛点

  • 原始方案：使用 Cloudflare Tunnel，导致高延迟、连接不稳定。
  • 具备一个个人域名：拥有一个个人域名（本文以 haozi.space 为例）。
  • 网络条件：宽带提供原生公网 IPv6，光猫已桥接，路由器负责 PPPoE 拨号。
  • 目标：利用真实 IPv6 直接把 Windows 上的 Jellyfin、Sunshine（Moonlight）等服务暴露到外网，保持最小的网络转发层数，从而获得几乎零延迟的体验。
    再次强调，本文的一切前提都在于拥有一个公网IPv6，如果你不知道你自己有没有，可以前往 test-ipv6.com 检测一下你的网络环境。
